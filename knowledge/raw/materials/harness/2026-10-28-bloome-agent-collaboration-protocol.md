## 一句话摘要

Bloome 的 agent 协作协议：当多个可见 agent（和人）在同一共享工作区里协作时，靠"分布式智能 + 共享协议"——agent 各自保留语义判断，环境提供共享任务状态、新鲜度感知与安全输出边界——来解决重复劳动、过期上下文、无合并结果这三大协调失败；最小验证基准是多个 agent 一起从 1 数到 20 不重复、不跳号。

## 主要要点

- **问题来源**: 多个 agent 共享同一公开环境时，失败模式不是 agent"不好"，而是各自按本地决策行动：重复同一部分工作、基于过期上下文回答、用户被迫当经理去重新分配、纠正、合并。
- **设计原则**: Distributed intelligence, shared protocol——语义归 agent（决定任务含义、是否参与、贡献哪部分、如何回应），事实归环境（任务状态、进度边界、新鲜度信号、输出安全）；人不被排除在环外，公开输出有边界。
- **三个必需能力**:
  1. 共享任务状态：共同的工作单元（相当于 issue / task / PR），说明目标、是否活跃、谁负责哪部分、已进展、是否完成；
  2. 新鲜环境感知：行动前（当前共享工作快照）、行动中（高信号变化）、发布前（避免过期公开输出）三个时刻感知 workspace 变化；
  3. 安全输出边界：发布前给 agent 一次基于新鲜事实重新决策的机会（修订或沉默），但边界不是语义裁判——不评判段落好坏、不决定正确答案，只呈现新鲜事实。
- **与中心协调器的区分**: 单 leader + 隐藏 subagent 适合"可当作一个私有任务"的工作（如 Anthropic 多 agent 研究系统，适合广度探索但协调开销与 token 成本高）；可见 agent 团队（人可直接点名任何 agent、任务在房间内演化、agent 来自不同 runtime/厂商/角色）需要分布式协议——不把所有工作压进一个 agent 的上下文窗口、一个规划循环、一个语义瓶颈，水平扩展。
- **GitHub 类比**（作者自认不完美，因 agent 冲突多为语义而非行级）: issue/project task → 持久共享任务状态；branch/ownership → agent 认领或划定责任；commit 关联 issue → 公开输出关联任务进度；PR/review → 人或 agent 的评审检查点；merge conflict → 过期、重复或不兼容的进展。
- **效率约束**: 协调只应落在高杠杆边界（工作创建或变形、认领有意义单元、公开输出会改变共享进度），不要让 agent 为每个想法申请许可；成功指标是更少重复、更少过期输出、更清晰进度、更低人工管理成本，而非更多 agent 活动。
- **生产教训（按先坏顺序）**: 新鲜度先坏（基于旧视图的好决策仍可能发布坏消息 → 需要更强的版本控制）；进度次坏（自然语言摘要会漂移 → 任务状态应更接近工作日志而非聊天摘要）；安全变"剧场"会拖慢效率（每个变化唤醒所有 agent、每条输出默认拦截 → 需要高信号路由）；所有权变 messy（部分、重叠、变化的所有权 → 冲突检查与划定责任）。
- **未来三方向**: 更强的版本与冲突语义（语义冲突：过期假设、重复进展、不兼容建议、他人已完成的工作）；依赖感知的任务管理（串行/并行之外，真实工作是依赖图）；人类评审成为协议状态而非例外（便于检查进度、重定向、批准输出、停止任务）。

## 适用场景

- 多 agent 可见协作的设计参考：任务状态、新鲜度、输出边界三件套
- 与 Reason Network 对照：Reason 解决"不同机器/工具的 agent 如何互相找到并通信"（连接层），Bloome 解决"同一房间内的 agent 如何不踩脚"（协作语义层）
- 评估多 agent 系统时区分"读多型"（天然并行）与"写多/进度型"（需要所有权、版本与合并点）

## 一句话摘要

Bloome 的多人记忆设计：单人记忆回答" 我知道什么"，多人场景必须先回答"这是关于这个人的、此刻还成立的吗"——解法是每人一套普通文件（无隐藏索引、无相似度分数）：卡片正面放每次对话都需要的事实（沟通偏好、严重过敏），其余放抽屉里按需直接打开文件查找；身份从"搜索要猜的东西"变成"这是谁的文件夹"。

## 主要要点

- **问题根源**: 单人助手的记忆是"一本笔记本"——长期事实笔记 + 近期日志，隐含主语永远是"你"。放进群聊后隐含主语消失："喜欢简短回复、不用 emoji"若不知是谁的偏好，就会误用。
- **为什么"全存下来再搜"救不了**: 检索按文本相似度匹配，返回的是"提到 Mike 的段落"而非"这个人"——两个都叫 Mike 的人无法区分；且检索结果不会自然过期（"Mike 计划去东京"行程结束后仍同样可搜到）。作者点评了两类主流做法：OpenClaw 的检索优先（全存下来、需要时搜），Hermes 的小而精人工档案 + 外部记忆服务按需取——两者对单人都好，但在共享空间都栽在"who"上。
- **设计：每人一套文件，可浏览而不只是可查询**:
  - 每人一小套普通文件，agent 直接打开读，无隐藏索引、无相似度分数居中；
  - 每条事实只做一次判断：放"卡片正面"（每次与此人对话都要看到，如沟通偏好、严重过敏）还是"抽屉"（真实、可取回，但不贴在额头上）；
  - 卡片正面必须短：什么都呈现的记忆等于什么都没呈现——关键事实会淹没在一百条不重要的里面；正面容量有硬上限（但作者承认上限只是兜底，不是好品味）。
- **召回机制借自 coding agent**: 文件记忆的经典失败是 agent 觉得抽屉"大概不相关"而不去看；解法是让 agent 像工程师找函数定义一样——需要时直接对文件做纯文本搜索、当场查找，而非维护一个猜相关性的索引。作者强调这不是换名头的"全搜"：没有索引要同步，事实以纯文本、按人分文件存放，"who"与"是否仍成立"几乎免费获得。
- **实测（作者自述，非严谨评估）**: 真实对话中抽屉里的事实（食物过敏、宠物名、旅行计划）被问到时正确召回；单条消息里的多条细节被合理分流（沟通偏好与过敏上正面、时效性项目细节进抽屉）；旧的单笔记本记忆在日常工作中被 agent 自行重组为新形态。作者明确谨慎：只是少量对话 + 强模型的结果，未测弱模型是否仍可靠开抽屉；agent 自行决定正面内容是否可信仍是开放问题。
- **开放问题**: 一人认识成百上千人时是否还成立；agent 能否被信任自己策展记忆（什么留正面、什么淡出）；"who-first"能否从人扩展到项目、团队、房间里的其他 agent。
- **核心论断**: 问题不在检索质量，而在记忆的"单位"错了——单本笔记本没有"who"的概念，纯相似度搜索也没有；共享空间把"who、且是否仍成立"变成第一问题，而最便宜的诚实答案是 coding agent 早已信任的东西：一人一套可直接读写的纯文本笔记。

## 适用场景

- 多人/多 agent 共享空间的记忆设计：身份优先于相似度
- 文件式记忆 vs 向量检索的取舍参考（"who"与"时效"免费获得 vs 索引同步成本）
- 与协作协议对照：记忆管"关于谁"，协作协议管"谁在干什么、进度到哪"
